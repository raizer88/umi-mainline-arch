# 90 Hz on the Samsung panel (`j2_p2_1_38_0c_0a`)

The bring-up shipped the panel at 60 Hz even though the hardware supports 90 Hz.
The mode data was there, but the panel was initialised with the 60 Hz
on-sequence and 60 Hz vertical timing.

## Where the truth comes from

The stock `dtbo` on the device carries both timings for every panel variant.
Dump it and read the node for the installed panel:

```sh
# on the phone
dd if=/dev/block/by-name/dtbo of=/tmp/dtbo.img bs=1M
```

The image is not an Android DTBO table (header `0xd7b7ab1e`, version 0): it is a
plain sequence of 12 concatenated FDT blobs. Split them by searching for the FDT
magic `d0 0d fe ed`, then decompile:

```sh
dtc -I dtb -O dts -o f00.dts f00.dtb
```

`f00.dts` contains every panel. On the field unit the installed one is
`qcom,mdss_dsi_j2_p2_1_38_0c_0a_dsc_cmd` (Samsung) with two timings:

| | `timing@0` (60 Hz) | `timing@1` (90 Hz) |
|---|---|---|
| `panel-framerate` | `0x3c` | `0x5a` |
| `v-back-porch` | `0x230` (560) | `0x08` (8) |
| `v-front-porch` | `0x258` (600) | `0x04` (4) |
| `v-pulse-width` | `0x20` (32) | `0x04` (4) |
| `h-front/back/pulse` | `0x10` / `0x08` / `0x08` | same |
| `panel-clockrate` | `0x28a67e80` | same |

Only the vertical porch changes: `vt` goes from 3532 to 2356 lines, and
`1112 × 2356 × 90 / 1000 = 235788 kHz` — the same pixel clock as 60 Hz.

The two `mdss-dsi-on-command` sequences are **identical except for two bytes**
inside the B4 table:

| | 60 Hz | 90 Hz |
|---|---|---|
| `0xB1` parameter (after `0xB0 0x05`) | `0x20` | `0x10` |
| DCS `0x53` brightness-control byte | `0x20` | `0x30` |

## What this means for the DTS

`dts/xiaomi-umi-panels.dtsi` is generated by `tools/gen-panel-dts.py` from the
*downstream* panel node, which stores only the default timing. To run at 90 Hz,
three values and two payload bytes are changed:

```dts
xiaomi,framerate = <0x5a>;      /* was 0x3c */
xiaomi,v-back-porch = <0x08>;   /* was 0x230 */
xiaomi,v-front-porch = <0x04>;  /* was 0x258 */
xiaomi,v-pulse-width = <0x04>;  /* was 0x20 */
```

and in `xiaomi,on-seq`: `... 0x02 0xb1 0x20 ...` → `0x02 0xb1 0x10`, and
`0x02 0x53 0x20` → `0x02 0x53 0x30`.

`xiaomi,clockrate` stays untouched: the driver uses it as the DSI bit clock and
the stock panel node declares the same value for both timings.

## Verify

```sh
dmesg | grep 'panel-xiaomi-umi.*mode:'
# 1080x2340@90, 1112x2356 total, 235788 kHz
```

Note the `@90` in the mode line and `2356` as the vertical total. If the mode
still says `@60` and `3532`, the DTB in the boot image is the old one — `pack-umi.py`
takes the DTB explicitly, so rebuild with `scripts/dtb-only.sh` first.

## Variant warning

These bytes are for the **Samsung** `j2_p2_1_38_0c_0a` panel only. The CSOT
`j2_mp_42_02_0b` variant uses a completely different B4 table — the
`miercolesvd/nura-mi10-umi-port` series patch 0006 has it (`0x2F 0x04`,
`0x26 0x02`, different gamma rows). Do not mix the two.

## Risk and rollback

Wrong timing data can leave a black panel while the kernel keeps running
(the display never leaves `prepare`). Keep a known-good boot image; the field
unit used:

```sh
adb push out/boot-before-90hz.img /tmp/ && \
  adb shell 'dd if=/tmp/boot-before-90hz.img of=/dev/block/by-name/boot bs=1M && sync'
```

from TWRP, since the Arch rootfs has no `adb`.
